# TwinPath — Feature Roadmap & Design Brief

Mission: financial freedom for Sergio & Brianna's family. Twins arrive
late Dec 2026 / early Jan 2027. Sergio starts at Iona (cybersecurity)
Aug 2026; Brianna is at DCC for nursing. Every feature below serves one
of three jobs: **see the money clearly, grow the money safely, automate
the boring parts with consent.**

Part A is buildable backend/data work (Claude's lane). Part B is
design-only guidance for Codex — no implementation here, just direction.

---

## Part A — Features, connectors, and financial routes

### A1. Plaid product expansion (highest leverage, data already flowing once Link works)
| Product | What it unlocks | Effort |
| --- | --- | --- |
| Transactions (live) | Everything below feeds off this | Done pending Link fix |
| Balance | Real-time "safe to spend" number | Small |
| Liabilities | Student loans + credit cards: APRs, minimums, payoff planning | Medium |
| Recurring Transactions | Auto-detected bills & subscriptions | Small (Plaid computes it) |
| Investments | Track brokerage/Roth when they open one | Medium, later |
| Income | Verified income streams for aid applications | Later |

Each follows the existing pattern: readiness gate, household-scoped
persistence table, worker route, sync cursor.

### A2. New financial routes (control-plane worker, all derived from data we already store)
- `GET /v1/financial/networth` — assets minus liabilities over time;
  snapshots into a `networth_snapshots` table nightly via cron.
- `GET /v1/financial/cashflow` — 90-day forecast from recurring inflows/
  outflows; flags the projected tightest week. A "twins runway" variant
  counts down to the due date with projected baby costs.
- `GET /v1/financial/recurring` — detected subscriptions & bills with
  "you could cancel this" candidates (unused subscriptions surface as
  agent proposals, never auto-cancelled).
- `POST/GET /v1/financial/goals` — savings goals (emergency fund, crib &
  gear fund, tuition gap) with progress computed from tagged transfers;
  `family_savings_routes` table already exists to build on.
- `GET /v1/financial/insights` — weekly agent-written digest (spend by
  category vs prior month, unusual charges, goal pace). Generated by
  cron, stored, surfaced in-app; doubles as the source of new proposals.
- `POST /v1/financial/import/csv` — manual CSV import for accounts Plaid
  can't reach (Venmo/Zelle exports, cash tracking). Validated, bounded,
  idempotent by hash.

### A3. Connector/plugin registry (make "many integrators" a data problem, not a code problem)
`src/connectorCatalog.js` already exists — promote that idea server-side:
a `connectors` registry where each entry declares auth type, webhook
verification, readiness requirements, and tables. New integrations become
registry entries + one adapter module, and `/v1/financial/connections`
lists them automatically. Priority order:
1. **Stripe live** (billing + storefront revenue) — machinery is built;
   needs live keys + price allowlist.
2. **Gumroad webhook → revenue_events** — storefront sales into the
   ledger; signature-verified like Stripe.
3. **CSV importer** (A2) as a universal fallback "connector."
4. Later: brokerage via Plaid Investments; credit-score tracking when a
   consumer-permissioned API is affordable.

### A4. Automation with consent (extends the proposals system just shipped)
- Weekly insights cron files proposals: "Gym sub unused 60 days — cancel
  it yourself and I'll track the $34/mo into the crib fund."
- Goal auto-pace: agent proposes adjusted weekly targets when income
  changes; approval updates the goal via flag payload.
- Guardrail unchanged: **nothing moves money autonomously — ever.** The
  agent computes, proposes, and tracks; humans move dollars.

## Part B — Design brief for Codex (no code here, direction only)

### B1. Information architecture
Today the app is feature-rich but flat — workspaces (Financial Hub, Grow,
Family, Profitability, Operations, Themes, Store) compete as peers.
Restructure around the three jobs:
- **Home** — one screen answering "are we okay?": safe-to-spend number,
  twins-runway countdown, goal progress, pending proposals badge.
- **Money** — accounts, transactions, recurring, goals, cash-flow
  forecast (absorbs FinancialHub + WalletPanel + FamilySavings).
- **Grow** — income streams, storefront/profitability, opportunities,
  career mission (absorbs Grow/Profitability/Opportunity workspaces).
- **Family** — gallery, calendar/appointments, twins checklist.
- **Settings** — themes, connectors, privacy lock, operations control.
Mobile: bottom tab bar with these five; the `feature/mobile-v3` instinct
was right.

### B2. The numbers are the interface
- One hero metric per screen, huge type. Home = safe-to-spend. Money =
  net worth. Grow = monthly income. Everything else is secondary.
- Trends as quiet sparklines next to metrics, not chart walls. Green/red
  only for meaningful deltas, never decoration.
- Currency formatting discipline: cents de-emphasized, negatives with
  color + sign (never color alone — see B5).

### B3. States before screens
Every panel needs designed empty/loading/error states before its happy
path. Empty states should sell the action ("Connect your bank to see
90 days of cash flow — 2 minutes"). Skeleton.jsx exists — use it
everywhere data loads; never spinner-on-white. Error states say what
happened and what to do, matching the worker's error messages (the Plaid
panel already surfaces real messages — design for them).

### B4. Proposals = the app's personality
The proposals inbox is TwinPath's signature. Design it like a
conversation: agent avatar, plain-language rationale, one-tap
approve/reject, and a visible "what changed" trail (flag flipped, route
appeared). A small badge on Home when proposals are pending. This is
where "the app improves itself with your permission" becomes a feeling.

### B5. Accessibility & trust (a finance app must feel bank-grade)
- Contrast: audit every theme against WCAG AA — dark themes with pastel
  accents (nursery, rose) likely fail on small text.
- `prefers-reduced-motion`: the three.js ThemeScene should drop to a
  static gradient; also consider disabling the 3D scene on low-power
  mobile by default (battery + jank).
- Focus states on every interactive element; the PrivacyLock flow should
  be reachable by keyboard alone.
- Numbers never conveyed by color alone; icons + signs accompany.
- Plaid/Stripe moments deserve explicit reassurance copy: "Credentials go
  to your bank via Plaid — TwinPath never sees them."

### B6. Performance & PWA polish
- Defer the three.js chunk until after first paint; Home should be
  interactive < 2s on a mid-range phone.
- The new offline.html is good — extend the SW toward cached last-known
  balances with a clear "as of" stamp when offline (read-only, clearly
  stale-marked).
- Route-level code splitting already exists; keep new features in their
  own lazy chunks.

### B7. Storefront
Separate visual identity from the private app (it has different users):
lighter, product-first, fast. One accent color from the brand, real
product photography/preview GIFs over abstract art, and trust signals
(refund policy link, secure-checkout badge) near every buy button.

## Sequencing (suggested)
1. Fix Plaid Link (production approval) → live transactions.
2. Codex: IA restructure + Home screen (B1/B2) while data accumulates.
3. Recurring + cash-flow routes (A2) → Home hero numbers become real.
4. Weekly insights cron → proposals inbox comes alive (A4/B4).
5. Stripe live + Gumroad revenue (A3) → Grow tab shows real income.
6. Liabilities + goals → payoff planning before spring semester.

The through-line: every sprint ends with a number on Home getting more
honest. That's the product.
